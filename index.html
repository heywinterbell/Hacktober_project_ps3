ClaimCheck
Triage that tests the claims.

Maintainers get bug reports, security reports, and pull requests full of promises. ClaimCheck runs each claim through deterministic checks and a hardened sandbox, then posts the verdict with the evidence — not an opinion.

Python CLI + GUI Docker sandbox Local open-weight LLM (Ollama) No cloud AI, no API keys github.com/heywinterbell/Hacktober_project_ps3
The problem

Maintainers drown in unverified claims

Every project that takes input from the internet gets three kinds of it. Most cannot be checked by hand, and the ones that are wrong still burn hours.

Bug reports

"Crash on long URLs"

No repro, wrong version, or already fixed. The maintainer has to re-derive it from scratch.

Security reports

"RCE in parse_url_v2()"

The symbol may not exist at all — but the claim reads plausible and demands a response.

Pull requests

"Fixes #120, adds tests"

"Adds tests" is a claim about coverage. Unchecked, it ships whatever the diff touched.

Triage cost is real: hours per false report, plus the risk of writing off a real one. Maintainers need evidence, not a second opinion.
The approach

Test the claim, show the evidence

ClaimCheck classifies the input, extracts the testable claims (symbols, versions, repro steps, changed lines), and answers each with a check that actually runs: AST lookup, git tags, a sandboxed execution, or diff × test-coverage intersection. The output is a Markdown evidence block a maintainer can act on in ten seconds.

The LLM never decides a verdict. Qwen2.5-Coder 7B (open-weight, local, via Ollama) only extracts claims and writes optional summaries. Every CONFIRMED / REFUTED / WARNING comes from deterministic code. The tool fully works with the model off.

Under the hood

Five stages, one hardened boundary

1 · Classify

Type the input

Bug, security report, or PR — routes to the right checks.

2 · Extract

Pull the claims

Rule-based always; local LLM (qwen2.5-coder:7b) optional. Symbols, versions, repro snippets, changed lines.

3 · Check

Deterministic verdicts

AST symbol lookup · git/package version · sandboxed repro · diff × pytest-coverage.

4 · Execute

Only in the sandbox

Untrusted code runs in Docker: no network, read-only fs, all caps dropped, resource + time limits.

5 · Report

Evidence, not opinion

Markdown report, or JSON for machines. Without Docker: restricted fallback, flagged isolation: weak on every line.

hunt mode — five hunter agents (SQLi · command injection · path traversal · XSS · RCE) generate payloads with the local LLM and execute them in the sandbox. Verdict from execution, never from the model.

Live evidence

What the tool actually outputs

Real output from running ClaimCheck against a sample Python package — not scripted examples. The tool reports both what it confirms and what it cannot run.

$ claimcheck doctor
Docker:   available
Ollama:   available

$ claimcheck triage --repo sample_project -r bug_report.md --no-llm
## Bug check
**Verdict:** ✓ confirmed  Isolation: **strong**
- ✓ symbol_exists: parse_url() exists (1 definition)
- ✓ version_exists: version 2.4.0 exists (tag 2.4.0)
- ✓ reproduction: Reproduced on 2.4.0 (crashed)
$ claimcheck triage --repo sample_project -r sec_report.md --no-llm
## Bug check
**Verdict:** ✗ refuted  Isolation: no code was executed
- ✗ symbol_exists: parse_url_v2() does not exist

$ claimcheck hunt "parse_url() has a SQL injection vulnerability in user input"
sql_injection      → SQL injection ruled out for 'parse_url'
command_injection  → Command injection test on 'parse_url': confirmed
path_traversal     → Path traversal ruled out for 'parse_url'
rce              → RCE test inconclusive for 'parse_url'
$ claimcheck pr --repo sample_project --diff-file feature.diff --no-llm
## Pr check
**Verdict:** ? inconclusive  Isolation: **strong**
- ? pr_coverage: could not run the test suite in the sandbox
   (the image only has pytest and pytest-cov, not the repo's own dependencies)

All three blocks are captured verbatim from real runs against the project's own sample fixture — the SQLi claim gets refuted by execution while a command-injection finding surfaces, and the PR check fails loudly with a reason instead of guessing.

Built safe

Safety, scope, and what's next

Safety by construction

  • Untrusted report code runs only inside sandbox.run_in_sandbox — no secrets, no network, read-only filesystem, dropped capabilities, hard resource and time limits
  • Static checks (AST) never execute repo code
  • Webhook payloads verified with HMAC SHA-256
  • Weak-isolation fallback is flagged on every report, never silent
  • No cloud AI, no API keys — runs on a machine with nothing but Python

Honest limits

  • Python repositories only (AST + pytest/coverage)
  • Full isolation needs Docker; without it the tool says so
  • Failure-description matching is heuristic
  • Kernel-level container escapes are out of scope
  • Next: ship the GitHub App webhook (serve) so reports are triaged in the PR thread automatically
